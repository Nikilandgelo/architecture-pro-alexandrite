## Мотивация
Операторы жалуются на медленную первую страницу MES: это дашборд со списком заказов в работе по
статусам. Каждый оператор при открытии и обновлении страницы отправляет в MES API запрос, который
идет в MES DB. Запросов много, они одинаковые, а данные новых доступных заказов у всех операторов
общие и меняются редко (только при смене статуса заказа). При росте числа заказов (+100 в месяц) и
числа операторов и API-клиентов нагрузка на MES API и MES DB будет расти, а скорость падать.
Для операторов это напрямую связано с деньгами: вознаграждение получает тот, кто взял заказ первым,
поэтому медленная страница означает для них упущенные заказы.

### Кеширование должно решить:
- медленную загрузку первой страницы MES для операторов;
- повторяющуюся нагрузку на MES DB одинаковыми запросами (нагрузка перестанет зависеть от числа
операторов).

Стоит сказать, что кеширование не заменяет решения из первого задания: основная причина медленной
работы MES API - это однозначно расчет стоимости, который будет вынесен в отдельный MES Worker.
Кеш лишь дополняет это решение и снимает оставшуюся нагрузку от дашборда.

### Что следует включить в кеширование:
- **Список заказов, ожидающих взятия оператором** (статус `MANUFACTURING_APPROVED`) на первой
странице MES. Читается всеми операторами постоянно, меняется только одним более быстрым оператором
при смене статуса.

### Было рассмотрено, но не включено:
- **Результаты расчета стоимости**: казалось, что имеет смысл также кэшировать результат долгой
работы процесса рассчета стоимости 3D модели, чтобы при загрузке одного и того же файла не вызывать
перерасчет, но т.к. цена может зависеть от внешних условий, таких как цена на определенный металл
в данную конкретную секунду, поэтому переиспользование одного и того же результата расчета может
быть не совсем корректным.

## Предлагаемое решение
### Тип кеширования
Выбрано **серверное кеширование** в `Redis`. Клиентское кеширование в данном случае не подходит:
данные должны быть свежими и общими для всех операторов, а сервер не может инвалидировать кеш в
браузере клиента когда заказ взял другой оператор. Браузер либо показывал бы устаревший список,
либо кеш был бы настолько коротким, что не имел бы смысла.

### Структура кеша
В `Redis` хранится один ключ типа `hash` с заказами, ожидающими взятия:
- ключ: `orders:awaiting`;
- поле: `order_id`;
- значение: JSON с данными, необходимыми для отображения на странице (номер заказа, время
создания, описание изделия, стоимость и т.д.). На ключ устанавливается TTL (например, 2-3 минуты)
как предохранитель: если фоновое обновление перестанет работать, ключ истечет, и API будет читать
из БД, а не показывать устаревший список.

### Паттерн: Refresh-Ahead
Выбран паттерн **Refresh-Ahead** в виде периодического фонового обновления: отдельная фоновая задача
каждые ~10 секунд читает из MES DB заказы в статусе `MANUFACTURING_APPROVED` и обновляет хеш в
Redis. API при чтении списка всегда обращается только в Redis. Если в Redis нет данных (например,
после перезапуска) или он недоступен, API читает из БД напрямую.

Почему именно этот паттерн, а не другие - паттерн **Refresh-Ahead** позволяет минимизировать
количество промахов кэша и всем читать из одного места в кэше, сколько операторов в MES бы не было.

### Стратегия инвалидации
Выбрана комбинация: **программная инвалидация по событию** плюс **временная (TTL и интервал
обновления) как страховка**.
- При взятии заказа оператором (`MANUFACTURING_STARTED`) MES API после успешного обновления в БД
выполняет `HDEL orders:awaiting <order_id>`, и остальные операторы перестают видеть этот заказ
сразу, не дожидаясь следующего обновления.
- Новые заказы в статусе `MANUFACTURING_APPROVED` попадают в кеш при очередном фоновом обновлении
(задержка не больше интервала ~10 секунд).
- Любые пропущенные изменения исправляются следующим фоновым обновлением, а при остановке самой
задачи ключ истечет по TTL.

Принцип целостности: источником истины остается БД, кеш только ускоряет чтение. Взятие заказа
выполняется только через БД условным обновлением (статус меняется на `MANUFACTURING_STARTED`,
только если он еще `MANUFACTURING_APPROVED`, с блокировкой строки); если обновлено 0 строк,
оператору возвращается ошибка "заказ уже взят". Порядок при взятии: сначала коммит в БД, затем
удаление из кеша. Наоборот нельзя: при сбое между шагами заказ исчез бы из кеша, хотя в БД он еще
доступен.

Сравнение стратегий инвалидации:

|                | Программная по событию + TTL (выбрана)                                | Только временная (TTL)                                                                                            | По ключу (удаление всего ключа списка) |
|----------------|-----------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------|----------------------------------------|
| Свежесть       | Взятый заказ исчезает сразу, остальное с задержкой не более интервала | Устаревший список до окончания TTL: либо операторы видят уже взятые заказы, либо TTL слишком мал и кеш бесполезен | Свежесть хорошая, но каждый сброс заставляет перечитывать весь список |
| Нагрузка на БД | Низкая, обновление раз в цикл                                         | Низкая, но платой за свежесть                                                                                     | Всплеск запросов после каждого сброса (при частых взятиях заказов) |
| Сложность      | Простая, нужно вызывать `HDEL` в одном месте (взятие заказа)          | Минимальная                                                                                                       | Простая, но неэффективная для нашего случая |
| Особенности    | Удаление точечное: меняется одно поле, а не весь список               | Не знает о событиях, взятый заказ остается в кеше                                                                 | Лишняя работа: из десятков заказов меняется один |

### Диаграмма последовательности
Показаны три сценария: фоновое обновление кеша, чтение списка заказов оператором и смена статуса
(взятие заказа). Участники: Оператор, SPA MES, MES API, фоновая джоба обновления, Redis, MES DB.
