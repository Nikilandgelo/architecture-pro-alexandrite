## Мотивация
Компания узнает о проблемах только из жалоб самих клиентов или операторов, то есть уже после того,
как пострадал бизнес и были либо просрочены заказы, либо заказы вовсе не были получены, либо система 
долгое время была недоступна.

Внедрение мониторинга даст:
- **Раннее обнаружение проблем**. Мы увидим рост очереди на расчет стоимости, всплеск ошибок или
перегрузку БД раньше, чем об этом нам сообщат клиенты. Это сокращает время обнаружения - *MTTD*.
- **Быстрое восстановление**. Метрики покажут, где именно находится проблема (API, расчет, БД или
очередь), поэтому команда потратит меньше времени на поиск причины.
- **Меньше потерь для бизнеса**. Чем короче простой и чем раньше будет замечена деградация системы,
тем меньше будет просроченных, потерянных заказов и обращений в поддержку.
- **Основа для решений**. Сейчас не до конца ясно, где именно узкое место, и невозможно проверить,
помогли ли улучшения. Метрики дадут точку отсчета (например, время расчета стоимости и длину очереди
ДО и ПОСЛЕ разделения MES API).
- **Планирование мощностей**. Нагрузка растет примерно линейно (+100 заказов в месяц), и по метрикам
будет видно заранее, когда ресурсы закончатся, до того как это произойдет в реальности и приведет к
сбою.

## Выбор подхода к мониторингу
Используем два подхода для разных частей системы:
- **USE** для инфраструктуры: EC2-инстансы приложений, инстансы БД и RabbitMQ. Для EC2 инстансов
используем *node_exporter*, для *RabbitMQ* встроенный Prometheus-плагин, для Managed БД метрики
из Yandex Cloud.
- **RED** для Shop API, CRM API и MES API (в том числе после разделения на API и
Worker). Метрики собираем через **OpenTelemetry** (Java agent для Shop и CRM, .NET SDK для MES) с
отправкой в OpenTelemetry Collector и далее в Prometheus.

## Список отслеживаемых метрик:
### RED (Shop API, CRM API, MES API; для MES после разделения отдельно API и Worker)
1. Количество запросов в секунду (RPS):
    - Зачем: видеть нагрузку, рост трафика и всплески от API-клиентов; основа для планирования
   мощностей. 
    - Ярлыки: `app`, `env`, `route` (шаблон пути, например `/orders/{id}`), `method`.
2. Количество ответов по статусам HTTP (200 и 500 одной метрикой):
    - Зачем: считать долю ошибок и сразу видеть деградацию сервиса. Вместо отдельных счетчиков
    200 и 500 используем один счетчик с ярлыком статуса.
    - Ярлыки: `app`, `env`, `route`, `status` (2xx, 4xx, 5xx).
3. Время ответа (latency):
    - Зачем: показывает, комфортно ли пользователям; важно для MES API, где долгий расчет раньше
    блокировал остальные запросы. Берем перцентили p50, p95, p99, а не среднее.
    - Ярлыки: `app`, `env`, `route`, `method`.
4. Объем переданных и полученных данных (Kb received / sent):
    - Зачем: через эти сервисы идут загрузки 3D-моделей, и по трафику видно аномалии и нагрузку на
   сеть.
    - Ярлыки: `app`, `env`, `route`.

### USE (инфраструктура)
5. % CPU (все EC2-инстансы приложений, RabbitMQ, инстансы Shop DB и MES DB):
    - Зачем: загрузка и насыщение вычислительного ресурса, для БД помогает отличить тяжелые запросы
    от нехватки памяти и соединений, у RabbitMQ перегрузка останавливает обмен между системами.
    - Ярлыки: `app`, `env`, `instance`.
6. Memory Utilisation (все EC2-инстансы приложений, RabbitMQ, инстансы Shop DB и MES DB):
    - Зачем: ловить утечки памяти и нехватку ресурса, у RabbitMQ при достижении memory watermark
    блокируется публикация сообщений.
    - Ярлыки: `app`, `env`, `instance`.
7. Количество соединений для Shop DB и MES DB:
    - Зачем: ловить исчерпание лимита подключений (рост числа инстансов приложений и воркеров
   повышает риск).
    - Ярлыки: `instance`, `env`, `state` (active, idle).
8. Размер Shop DB и MES DB на диске:
    - Зачем: контролировать рост данных и вовремя расширять хранилище.
    - Ярлыки: `instance`, `env`.
9. Размер S3-хранилища:
    - Зачем: объем 3D-моделей растет вместе с числом заказов, нужно видеть рост и лимиты.
    - Ярлыки: `bucket`, `env`.

### RabbitMQ
10. Число сообщений in flight (unacknowledged):
    - Зачем: показывает, сколько сообщений прямо сейчас обрабатывается; при долгих расчетах помогает
    заметить «зависшие» задачи и риск повторной доставки.
    - Ярлыки: `queue`, `env`.
11. Число сообщений в dead-letter exchange:
    - Зачем: любое ненулевое значение означает потерянный или не обработанный заказ, то есть
    напрямую связано с жалобами «не получили заказ».
    - Ярлыки: `queue`, `env`.

### Дополнительные метрики:
12. Глубина очереди:
    - Зачем: главный индикатор насыщения очереди, на основе глубины можно настроить масштабирование
    воркеров.
    - Ярлыки: `queue`, `env`.
13. Время расчета стоимости заказа:
    - Зачем: видеть, как растет время расчета (в норме 2-3 минуты, до 30 для сложных моделей).
    - Ярлыки: `env`, `complexity` (small, medium, large по числу полигонов).
14. Число заказов по статусам и время нахождения в статусе:
    - Зачем: бизнес-метрика, которая напрямую показывает, где заказы зависают (особенно между
    `SUBMITTED` и `PRICE_CALCULATED`).
    - Ярлыки: `status`, `source` (shop, MES api), `env`.

## План действий
1. Поднять один инстанс Prometheus и один инстанс Grafana на отдельном EC2 вне окружений приложений
с хранением метрик на диске.
2. Использовать OpenTelemetry Collector для приема метрик приложений по OTLP и передачи их в
Prometheus.
3. Подключить OpenTelemetry Java agent к Shop API и CRM API (Spring Boot).
4. Подключить OpenTelemetry SDK к MES API и MES Worker (C#, ASP.NET Core instrumentation).
5. Добавить в код пользовательские метрики: время расчета (гистограмма в MES Worker через
OpenTelemetry) и метрики заказов (количество заказов по статусам и возраст самого старого заказа в
статусе через SQL-запросы к БД, время нахождения в статусе при каждой смене статуса). При 
необходимости добавить в таблицу заказов поле времени последней смены статуса.
6. Установить node_exporter на EC2-инстансы приложений; включить встроенный Prometheus-плагин
RabbitMQ; настроить получение метрик Managed-БД и S3 из Yandex Cloud.
7. Построить дашборды в Grafana: единый шаблон RED для всех API, шаблон USE для инфраструктуры,
отдельный дашборд по очереди и заказам.
8. Развернуть Alertmanager и настроить уведомления (Telegram, Slack или почта) для команды.
9. Настроить алерты на критические значения метрик (ошибки 5xx, рост очереди, DLX, загрузка CPU и
памяти, нехватка соединений к БД, рост latency); Алерты для прода можно отправлять в основной канал,
алерты же для dev и release можно или отключить или направить в отдельный канал, чтобы не создавать
шум.
10. Подключить сбор метрик во всех окружениях (dev, release, prod) с ярлыком `env`.

## Дополнительное задание
Показатели насыщенности выбраны там, где ресурс или очередь упираются в предел и это уже влияет на
заказы. Пороги стартовые, после нескольких недель сбора метрик их можно скорректировать по реальным 
данным, чтобы не получить ложных срабатываний.

| Показатель                                        | Warning                    | Critical                        | Почему именно он                                                                                          |
|:--------------------------------------------------|--------------------------- |-------------------------------- |---------------------------------------------------------------------------------------------------------- |
| Глубина очереди на одного воркера                 | > 5 в течение 10 мин       | > 20 в течение 10 мин           | Прямой признак того, что воркер не успевает за потоком сообщений                                          |
| Возраст самого старого заказа в `SUBMITTED`       | > 40 мин                   | > 2 часа                        | Расчет занимает до 30 минут, поэтому все, что дольше значит зависло. Метрика привязана к бизнесу и срокам |
| Сообщения в dead-letter exchange                  | —                          | > 0                             | Любое сообщение здесь означает не обработанный или потерянный заказ                                       |
| Доля ответов 5xx для API                          | > 1% в течение 5 мин       | > 5% в течение 5 мин            | Показывает деградацию сервиса для пользователей и API-клиентов                                            |
| Latency p95 (API)                                 | > 2 с в течение 5 мин      | > 5 с в течение 5 мин           | Операторы и клиенты замечают именно «хвост», а не среднее                                                 |
| CPU инстансов (приложения, RabbitMQ, БД)          | > 80% в течение 5 мин      | > 90% в течение 5 мин           | Выше этого уровня растут задержки, а запаса на пики нет                                                   |
| Memory инстансов                                  | > 80% в течение 5 мин      | > 90% в течение 5 мин           | Нехватка памяти ведет к свопингу и падениям; у RabbitMQ при watermark блокируется публикация              |
| Соединения к БД                                   | > 70% от лимита            | > 90% от лимита                 | При исчерпании лимита приложения не могут работать с БД; риск растет с числом инстансов и воркеров        |
| Место на диске БД                                 | > 75%                      | > 90%                           | Заполнение диска останавливает запись; рост данных предсказуем и заметен заранее                          |
| Размер S3                                         | Заполнено > 80% от квоты   | Заполнено > 95% от квоты        | Объем 3D-моделей растет вместе с заказами                                                                 |

Что происходит при превышении (в рамках первой версии только алерты, без автоматических действий):
- Warning: уведомление в рабочий канал (Telegram, Slack, т.д) и заведение тикета, который берет в
работу дежурный инженер в рабочее время.
- Critical: уведомление в "критичный" канал с тегом дежурного, ожидается его немедленная реакция.

Автоматические действия можно будет добавить позже, когда будут накоплены данные для надежных
порогов.
