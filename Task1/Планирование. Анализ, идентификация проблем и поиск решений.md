## Существующие и потенциальные проблемные места:
- MES API монолитен: в одном сервисе совмещены расчет стоимости, назначение заказов операторам и
отдача списка заказов. Тяжелые расчеты отнимают ресурсы у API, из-за чего страдают операторы
(медленная первая страница MES) и API-клиенты. Фильтры по статусам и пагинация не помогли, значит
проблема не в объеме выдачи, а в перегрузке самого API сервиса;

- Расчет стоимости не успевает за ростом нагрузки (+100 заказов в месяц, линейно). Очередь на расчет
растет, заказы долго висят до статуса `PRICE_CALCULATED`, сроки сорваны;

- Открытый API для партнеров добавил нагрузку на расчет без изоляции от остального трафика. Нет
(или не описано) rate limiting и защиты от злоупотреблений: один партнер может занять весь расчет
и ухудшить сервис остальным, а также возможен DDoS;

- Интеграция MES и CRM через RabbitMQ: не описаны гарантии доставки и идемпотентность. Есть риск
потери или дублирования сообщений, а долгие обработчики (до 30 минут) могут не уложиться в таймаут
подтверждения и привести к повторной доставке. Это объясняет жалобы API-клиентов
"не получили заказ";

- Единые точки отказа и отсутствие масштабирования: по одному инстансу каждого приложения (EC2) и по
одному инстансу каждой БД на запись и чтение. Нагрузка растет, а ресурсы статичны. MES DB вообще 
обслуживает и расчет, и назначение операторам, и дашборд, и API, и это все это на одном инстансе;

- CRM API совмещает обычный CRUD для продавцов и прием сообщений о новых заказах из брокера;

- Процесс релиза: ручной деплой в release и prod, ручное E2E одним QA, баги high/highest блокируют
релиз. Задержки релиза уже выросли с одного месяца и продолжают расти, из-за чего исправления из
этого списка будут выкатываться еще дольше.

## Инициативы, которые необходимы для устранения нежелательных ситуаций:
1. MES API разбить на 2 сервиса, один который реально API круды для API Users и для операторов, в
то время как воркер вычитывает из брокера и делает расчет стоимости из 3д моделей. Воркер следует
реализовать с учетом паттерна Backpressure и забирать сообщения из брокера по pull модели в своем
темпе. Воркеры с консюмерами следует запускать в нескольких инстансах, количество зависит от глубины
читаемой очереди;

2. Обязательное обеспечение гарантии доставки хотя бы `At least once` при чтении сообщений из
брокера консюмерами (если этого еще нет) с реализацией идемпотентности на стороне консюмеров;

3. Добавить базовую защиту для MES API (при ее отсутствии) от потенциально злоумышленных действий
пользователей API, такую как: rate limiting, защиту от DDOS атак;

4. Снизить нагрузку и убрать единую точку отказа для БД, в первую очередь для MES DB: добавить
read-реплики и перенести на них запросы чтения, а запись оставить на основном инстансе. Перед БД
также добавить пулер соединений (если его еще нет), чтобы рост числа инстансов приложений и воркеров
не исчерпал лимит подключений и в целом, для более эффективной работы с БД приложениями;

5. CRM API также бы разбить на 2 сервиса, один который реально API круды для CRM и другой
вычитывает из брокера новые заказы от пользователей API через MES API и кладет туда сообщения;

6. Автоматизировать деплой в release-окружение (сейчас ручной), чтобы автотесты могли запускаться
сразу после выкладки. Деплой в prod оставить ручным, если все автотесты зеленые;

7. Автоматизировать E2E-тестирование: текущий QA пишет автотесты, начиная с критичных путей
(жизненный цикл заказа от `INITIATED` до `CLOSED`, заказ через API), затем расширяет покрытие.
Автотесты запускаются автоматически после мерджа в dev и release. Ручное тестирование остается
только для нового функционала, чтобы уменьшить задержки релизов;

8. Нанять второго QA: текущий переключается на автоматизацию, а ручное тестирование нового
функционала и еще не автоматизированных регрессий должен кто-то вести, иначе релизы замедлятся еще
сильнее.


### Видение целевой архитектуры через полгода:
MES разделен на два сервиса: легкий MES API (CRUD для операторов и API-клиентов) и MES Worker
(расчет стоимости). Воркеры запускаются в нескольких инстансах (несколько EC2 за общей очередью),
их количество автоматически подстраивается под глубину очереди в RabbitMQ. Каждый воркер берет
задачи по pull-модели в своем темпе (backpressure), не перегружаясь. Сообщения между MES, CRM и
магазином доставляются минимум один раз, консюмеры идемпотентны, поэтому заказы не теряются и
не дублируются.

Перед MES API стоит защитный слой (rate limiting, защита от DDoS), поэтому один партнер не влияет
на остальных. CRM API разделен на два сервиса: CRUD для продавцов и воркер для работы с RabbitMQ.
Приложения запущены в нескольких инстансах за балансировщиками. БД имеют read-реплики и пулер
соединений, а чтение вынесено на реплики, прежде всего в MES DB.

Процесс разработки: деплой в dev и release автоматический, после него сами запускаются E2E-автотесты
критичных путей, в prod выкатываются только версии с зелеными тестами. Команда QA из двух человек:
один развивает автотесты, другой тестирует новое вручную. Задержки релизов сокращаются.


### Если бы была возможность выполнить только три пункта из списка инициатив в ближайшие полгода, то я бы выбрал первые 3 по приоритету:
- П.1 (разделение MES API и масштабируемый воркер) - это корневая причина: расчет не успевает за
ростом заказов и блокирует остальной MES, из-за чего и просрочены заказы, и тормозит дашборд.
- П.2 (гарантия доставки и идемпотентность) - без нее масштабирование воркеров не поможет: заказы
все равно будут теряться или дублироваться, а именно эти потери видят клиенты и API-пользователи.
- П.3 (защита MES API) - самая прямая связь с деньгами: из-за заказов API-клиентов компания уже
теряет контракты, а без ограничений один партнер может снова перегрузить расчет.

Остальные инициативы важны, но не лечат текущие жалобы так напрямую. БД (п.4) выигрывает от п.1,
потому что нагрузка на MES DB упадет после выноса расчета; на линейном росте в сотни заказов в месяц
она не критична. П.5 затрагивает продавцов (их немного), а процессные пункты (6-8) ускоряют
выкладку исправлений, но не устраняют причины сбоев.
